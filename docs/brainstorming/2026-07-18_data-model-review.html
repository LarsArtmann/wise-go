wise-go Data Model Review

A first-principles review of every type in types.go, ids.go, errors.go, and the request/response structs. The existing model is already disciplined — branded IDs, two-layer raw/result split, int64 cents. This review catalogs what separates it from a model where invalid states are unrepresentable, not merely rejected at runtime.

The model is structurally sound. The raw-vs-result split correctly isolates the JSON-decode layer from the public API. Branded IDs (ProfileID, BalanceID, TransactionID) already eliminate an entire class of "passed the wrong ID" bugs at compile time. The error types compose via embedding and classify behaviorally via go-error-family.

The remaining problems cluster around two systemic roots: (a) money is modeled as paired primitive fields instead of a value object, and (b) several domain enums remain stringly-typed. Both are classic "organic growth" patterns — easy to write once, expensive to maintain, and exactly what this skill exists to correct.

01Problem Catalog

Critical · P9

Money is smashed into primitive pairs

Where: Transaction (6 pairs), TransactionExchange (2 pairs), BalanceResult (2 pairs).

Every monetary amount is modeled as XxxCents int64 paired with XxxCurrency string. Transaction alone has twelve fields for four logical amounts. Nothing prevents constructing a Transaction with TotalCents in USD but TotalCurrency set to "EUR". The pairing is an invariant the type system does not enforce.

Fix Introduce a Money value object. Each pair collapses to one field. Mismatched currency/amount becomes unrepresentable.
Critical · P1 / P4

Currency is a raw string

Where: every Currency string field, ListTransactionsRequest.Currency, BalanceAmount.Currency.

ISO 4217 currency codes are a closed, well-known set of exactly 3 uppercase letters. Modeling them as string means any caller can pass "usd", "USD ", "euros", or "" and the type system will not help. The empty-string case is so real that ListTransactionsRequest.validate() already special-cases it.

Fix type Currency string with a constructor that validates length-3 uppercase ASCII. Pairs naturally with Money.
High · P1

InvestmentState is untyped constants

Where: types.go:192-195, used in balances.go:28.

InvestmentStateNotInvested and InvestmentStateInvested are bare string constants with no named type. The filter at balances.go:28 compares b.InvestmentState != InvestmentStateNotInvested against an untyped string. Adding a third state in the future would silently slip past this. Compare to BalanceType and ProfileType, which are properly typed — this is an inconsistency within the same file.

Fix type InvestmentState string with the two constants promoted to that type. Add a parseInvestmentState helper that returns an error for unknown values.
High · P1

ListTransactionsRequest.Type is a raw Wise detail-type string

Where: types.go:221, serialized at transactions.go:33.

The Type filter accepts Wise's details.type wire values (CARD_PAYMENT, TRANSFER, etc.). These are the same values the SDK already has as unexported constants (wiseDetailCardPayment, etc.) — but the request field is string, so callers cannot discover the valid set without reading the README. The constants exist but are kept private.

Fix Export a typed DetailType enum and use it in the request. Existing string callers can keep working via a String()-based setter or by leaving the field as string but documenting the closed set.
High · P3 / P10

ListTransactionsResponse.HasMore is a documented lie

Where: types.go:227, hardcoded at transactions.go:66.

The field is always false. AGENTS.md documents this. The README documents this. And yet the field exists, promising pagination semantics that the type does not deliver. A caller writing for resp.HasMore { fetchMore() } will loop zero times and silently produce an incomplete dataset if Wise ever changes the contract. The field makes an impossible state representable — the opposite of the type-system goal.

Fix For v1.0: remove HasMore entirely and let ListTransactionsResponse be a plain []Transaction. For v0.x: at minimum rename to HasMoreOrEq... no — better: document why it exists (forward compatibility) in a comment, and never write HasMore: true in tests.
Medium · P3

Enum value casing is inconsistent

Where: types.go:178-209.

ProfileType values are lowercase (personal, business) — normalized from the API's PERSONAL/BUSINESS. BalanceType values are uppercase (STANDARD, SAVINGS) — passed through from the API verbatim. TransactionType values are lowercase (card, credit) — normalized from CARD_PAYMENT, etc. Two normalization strategies coexist in the same file. There is no single rule a contributor can follow.

Fix Pick one rule: "result enums are always lowercase Go-style; raw values stay wire-style." Then BalanceType should normalize to standard/savings for consistency — or all three stay wire-style. Either is defensible; the mix is not.
Medium · P3

TransactionTypeUnknown is dead

Where: types.go:209.

TransactionTypeUnknown is defined but never returned by classifyTransactionType — the default branch falls back to Credit or Debit based on amount sign. The constant is dead weight that implies a classification path that does not exist. Either remove it, or use it as the fallback when the detail type is unrecognized (preserving the information that classification failed).

Medium · P9 / P11

Duplicated enum-parsing functions

Where: profiles.go:57-66, balances.go:91-100.

parseProfileType and parseBalanceType are the same function shape: a switch over a string mapping to a typed enum, with a default error. Adding parseInvestmentState and parseDetailType would add two more copies. A single generic helper eliminates the pattern.

Fix 
func parseEnum[T ~string](table map[string]T, raw string, kind string) (T, error) {
    if v, ok := table[raw]; ok {
        return v, nil
    }
    var zero T
    return zero, fmt.Errorf("unknown %s %q", kind, raw)
}
Low · P3

Transaction.Date timezone semantics are undocumented

Where: helpers.go:44-51, transactions.go:76.

Wise returns transaction dates as "2006-01-02 15:04:05" with no timezone. time.Parse interprets this as UTC. Whether the original statement is in UTC, the account's timezone, or the currency's home timezone is not documented. A caller comparing tx.Date to a local time will silently off-by-a-day at boundaries.

Fix Document the assumption in the parseWiseDate doc comment and in the Transaction.Date field doc: "Returned in UTC; Wise does not transmit a timezone."

02The Vision

+
Money is a value object, not a field pair One Money type carries cents + currency together. A transaction has four Money fields, not twelve primitive fields.
+
Currency is branded and validated at construction An empty or malformed currency cannot reach the API layer because it cannot be constructed.
+
Every enum is a named type with a parser No bare string constants. InvestmentState, DetailType join ProfileType, BalanceType, TransactionType.
+
Enum parsing is one generic helper, not N copies parseEnum[T] eliminates the duplicated switch functions.
+
Responses do not promise what they cannot deliver HasMore is gone (or honestly named). TransactionTypeUnknown is gone (or used).
+
One normalization rule for all result enums Lowercase Go-style for SDK-facing enums; wire values stay wire-side in the raw layer only.

03Proposed Go Data Model

Money and Currency

// Currency is an ISO 4217 currency code (e.g. "USD", "EUR").
// Construct with NewCurrency; the zero value is intentionally invalid.
type Currency string

// NewCurrency validates a 3-letter uppercase ASCII currency code.
func NewCurrency(s string) (Currency, error) {
    if len(s) != 3 {
        return "", fmt.Errorf("currency must be 3 letters, got %q", s)
    }
    for _, r := range s {
        if r < 'A' || r > 'Z' {
            return "", fmt.Errorf("currency must be uppercase ASCII, got %q", s)
        }
    }
    return Currency(s), nil
}

// Money is a monetary amount in minor units of a currency.
// The zero value is "0 cents in no currency" — construct with NewMoney
// to enforce the currency invariant.
type Money struct {
    Cents    int64
    Currency Currency
}

func NewMoney(cents int64, cur Currency) Money {
    return Money{Cents: cents, Currency: cur}
}

// FromBalanceAmount converts a raw wire BalanceAmount (float64 major units)
// to precision-safe Money (int64 minor units).
func moneyFromBalance(a BalanceAmount) Money {
    return Money{Cents: a.Cents(), Currency: Currency(a.Currency)}
}

Redesigned result types

type Transaction struct {
    ID             TransactionID
    ProfileID      ProfileID
    BalanceID      BalanceID
    Amount         Money   // absolute value, always positive
    Fees           Money
    Total          Money   // signed: negative for debits
    RunningBalance Money
    Exchange       *TransactionExchange
    Type           TransactionType
    Description    string
    Reference      string
    Category       string
    MerchantName   string
    Date           time.Time
}

type TransactionExchange struct {
    From Money
    To   Money
    Rate float64
}

type BalanceResult struct {
    ID              BalanceID
    Currency        Currency
    Type            BalanceType
    Name            string
    Amount          Money
    Reserved        Money
    Visible         bool
    CreatedAt       time.Time
}

type ListTransactionsRequest struct {
    ProfileID ProfileID
    BalanceID BalanceID
    Currency  Currency
    From      time.Time
    To        time.Time
    Type      DetailType // zero value means "no filter"
}

The Transaction struct drops from 20 fields to 14, and every monetary amount now carries its currency by construction. The previous impossible state — TotalCents in one currency and TotalCurrency in another — is now unrepresentable.

Error composition: already correct

The error model is the part of the codebase that already uses composition well. RateLimitError, AuthError, NotFoundError, and ServerError embed APIError by value and override only the methods that differ. The base type carries StatusCode, Message, Body, Error(), ErrorCode(), and a default ErrorFamily(). Subtypes override ErrorFamily() (transient vs. rejection), IsRetryable(), and ErrorContext() as needed.

This is the textbook Go composition pattern — no deep inheritance, no abstract base classes, behavior overridden at the edge. It is called out here so reviewers do not "fix" something that is not broken.

05Validation Layer

The principle: if a value can be invalid, it must not be constructible. The redesigned model pushes validation into constructors so call sites never re-validate.

06Decision Log

Decision: Money is a struct, not [2]int64 or a typed int64

Chosen: struct { Cents int64; Currency Currency }. Rejected: a typed int64 with the currency in a parallel slice (data locality argued for it); a generic Money[T Currency] (overkill, currencies are not a compile-time set). The struct wins because it composes by value, zero-copy, and the pair is the natural unit — you never add cents across currencies.

Decision: Currency is a named string, not an int enum

Chosen: type Currency string with constructor validation. Rejected: a closed int enum (would require a registry and prevent callers from using currencies Wise has not added yet); an iota of "known" currencies (same problem, worse). A validated named string keeps the wire format readable while rejecting malformed values at construction.

Decision: InvestmentState joins the typed-enum pattern

Chosen: promote to type InvestmentState string. Rejected: leave as bare constants "because there are only two values." Two-value enums grow. The cost of typing it is one line; the cost of leaving it is a silent future bug when Wise adds HELD or PENDING.

Decision: Do not introduce interface-based union for Transaction

Chosen: keep Transaction a flat struct with a Type field and optional Exchange. Rejected: a sealed interface union (CreditTx, DebitTx, ExchangeTx ...). A union would force every caller ranging over []Transaction to type-switch, which is the wrong ergonomic for statement iteration. The optional Exchange pointer is the right trade-off for read-heavy SDKs.

Decision: defer HasMore removal to v1.0

Chosen: keep HasMore in v0.x, remove in v1.0. Rationale: the field is part of the public API today; removing it is a breaking change. The project is pre-1.0 and breaking changes are expected, but the data-model review is not the right scope for an API break — that belongs in a deliberate release. For now: add a comment explaining why it is always false.

07Anti-Patterns to Avoid

Do not brand the raw API structs

Profile, Balance, StatementTransaction exist to match Wise's JSON wire format exactly. Branding Profile.ID int64 into a branded type breaks encoding/json unmarshaling and creates false positives for phantom-ID linters. The raw layer stays primitive; the result layer gets the types. This is already correct — keep it.

Do not introduce a Money[T Currency] generic

Tempting for "type-safe cross-currency arithmetic," but currencies are a runtime value, not a compile-time set. Generic Money would force code generation or a massive type-set for no real safety gain over the validated-string Currency.

Do not add a Validate() method to every type

If you need Validate(), the type allows invalid states. The fix is to make the constructor the only way in and have it reject invalid input. Money, Currency, and the typed enums do not need Validate() because they cannot be constructed invalid. The only validate() that should remain is on ListTransactionsRequest, where the invariant (From <= To) genuinely cannot be encoded in the field types.

08Migration Roadmap

The roadmap is ordered by value ÷ risk. Each step is independently shippable. The project is at v0.2.0; pre-1.0 means breaking changes are acceptable but should still be deliberate.

1

Type InvestmentState + generic parseEnum helper

Internal-only, zero API break. Promote the two constants to type InvestmentState string; introduce parseEnum[T ~string]; refactor parseProfileType and parseBalanceType onto it. Ship as v0.2.1.

2

Export DetailType for ListTransactionsRequest.Type

Backward-compatible if done carefully. Promote the unexported wiseDetail* constants to exported DetailType values; add a type DetailType string. Keep the request field as string for now but document the closed set. Ship as v0.2.2.

3

Introduce Money and Currency (breaking)

v0.3.0 — the breaking release. Add Money, Currency, NewCurrency, NewMoney. Migrate Transaction, TransactionExchange, BalanceResult, and ListTransactionsRequest. Update tests, README, AGENTS.md. This is the centerpiece of the redesign and the change that pays for all the rest.

4

Normalize enum casing + reconcile dead values

v0.3.0 (same release as step 3). Pick one enum-casing rule (suggest lowercase for SDK-facing enums). Either use or remove TransactionTypeUnknown. Add a comment to HasMore explaining it is always false until v1.0 removes it.

5

v1.0: remove HasMore, lock the contract

v1.0. Drop ListTransactionsResponse entirely; ListTransactions returns []Transaction directly. Document the UTC assumption on Transaction.Date. Freeze the public API.

Conclusion

The wise-go data model is already disciplined — it gets the hard things right (branded IDs, two-layer split, behavioral errors). What separates it from a model where invalid states are unrepresentable is one missing value object (Money), one missing branded primitive (Currency), and finishing the typed-enum pattern it already started. None of these are speculative refactorings — every one of them removes a class of bug the current model pushes onto the caller.
