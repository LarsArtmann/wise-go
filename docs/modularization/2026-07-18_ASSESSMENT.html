Why Staying Single-Module Is Correct

Composition is already optimal

A consumer who wants only profiles imports github.com/larsartmann/wise-go and uses client.ListProfiles. The compiler pulls in everything. Splitting into wise-go-profiles, wise-go-balances, wise-go-transactions would force consumers to import three modules to do what one import does today — a net loss in composability, the opposite of Unix philosophy.

Co-change is total, by construction

types.go, client.go, and the resource files all change together for any feature addition. There is no independent evolution path. Module boundaries that are crossed by every commit are artificial — they impose cost without payoff.

The two-layer type system is one design unit

Raw wire types, mapping functions, and result types form a single anti-corruption layer. Splitting them across modules would either expose raw wire types publicly (bad — breaks encapsulation) or force awkward interface modules (bad — over-engineering for ~1k LOC). The current convention of two-layer separation inside one package is the right shape for this scope.

Dependencies are already isolated to the production code

The three production dependencies (failsafe-go, go-branded-id, go-error-family) are focused, stable, and each pulled by a single file (client.go, ids.go, errors.go respectively). There is no transitive bloat to isolate. Test deps (ginkgo, gomega) sit correctly in the test files and never leak into production go.mod.

Anti-Recommendations (Do Not Do These)

Rejected · Premature

Do not split per resource

wise-profiles, wise-balances, wise-transactions as separate modules. Every consumer would import all three. The boundaries have no composability payoff — the classic FM#8 (over-modularization) failure mode.

Rejected · Premature

Do not split raw/result types into separate modules

wise-wire (raw JSON types) + wise (result types). The result layer consumes the raw layer; consumers consume the result layer. Two modules, one consumer of the seam, zero payoff. Use a within-package internal/raw subpackage if raw-type leakage becomes a problem (architecture-review step 5).

Rejected · Premature

Do not extract a "domain core" module

Tempting pattern: wise-domain with pure types and interfaces, wise with the HTTP implementation. Justified for infrastructure plug-in swapping (e.g., multiple HTTP backends). wise-go has one implementation, one transport, one retry library. The seam would be unused.
