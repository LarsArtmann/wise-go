wise-go Architecture Review

How scalable, modular, service-oriented, and composable is the wise-go SDK? The short answer: intentionally minimal, correctly so. The longer answer: this review maps every file, dependency, and coupling edge in the package, then identifies the exact point at which the current flat design should give way to a more service-oriented shape — and what that shape should be.

wise-go is a deliberately flat, single-package Go SDK that wraps the Wise (TransferWise) REST API. It is in the early phase of the architecture lifecycle: 3 resources implemented (profiles, balances, transactions), all read-only, all in one package wise. For this scope, the flat design is correct — it minimizes import paths, eliminates artificial boundaries, and matches how callers actually use the library. The review identifies the exact growth signals that should trigger a move to a more service-oriented shape.

01Structure

The package has a clear internal分层, expressed through file boundaries:

package wise ├── ids.go Branded ID phantom types + constructors (zero deps) ├── types.go All public types: raw wire + parsed result + enums + requests ├── options.go Functional options (With* config setters) ├── helpers.go Body parsers, date parsers, Retry-After parser ├── errors.go Domain error types + status→type factory ├── client.go HTTP core: Client struct, New(), retry executor, getWithQuery ├── profiles.go ListProfiles resource method + mapProfile ├── balances.go ListBalances + GetBalance + mapBalance └── transactions.go ListTransactions + classify + mapTransaction + validate

Every file has a single responsibility. Every file's role is obvious from its name. The dependency direction is strictly downward in this list — resource files depend on client/types/helpers/ids/errors, never the reverse. There are no cycles, no god files, no grab-bag utilities.

03Scalability

Growth axes and how the architecture responds

+ Adding a new resource (e.g. transfers, recipients, quotes)

One new file (transfers.go) following the existing shape: a method on *Client, a mapTransfer function, types in types.go. Cost: O(1) files, O(1) decisions. No refactoring. Scales cleanly to ~8 resources.

+ Adding a new error type

One new struct embedding APIError, one new ErrorCode() method, one new case in newAPIError(). Existing call sites and retry logic are untouched. Scales indefinitely.

+ Adding a new configuration option

One new WithX() function in options.go, one new field on the unexported config struct, one new branch in New(). Scales indefinitely.

+ Adding write operations (POST/PATCH/DELETE)

Add a post()/patch()/delete() helper alongside get()/getWithQuery() in client.go. Same retry executor, same error checking, same body lifecycle. The architecture is ready.

~ Adding pagination (when Wise eventually requires it)

The current ListTransactionsResponse.HasMore is a forward-compatibility stub. If Wise adds cursor pagination, the architecture supports adding a Page[Cursor] generic and a FetchMore method without breaking the existing API. ListTransactionsResponse gains a NextCursor field. No client-struct change needed.

− Adding request middleware (logging, tracing, metrics)

This is the only architectural gap. The current code routes every request through getWithQuery, which is unexported. Callers who want to add OpenTelemetry tracing, structured logging, or metrics must either (a) wrap via WithHTTPClient with a custom http.Client + Transport, or (b) forgo the SDK's retry layer entirely. Option (a) works but is not obvious. The README should document this pattern; see Roadmap step 2.

04Composability

+
Functional-options pattern is composable by construction wise.New(key, WithSandbox(), WithTimeout(...), WithRetry(...), WithHTTPClient(...)) — every WithX is independently combinable. Adding new dimensions of configuration never breaks existing call sites.
+
HTTP client is injectable WithHTTPClient(*http.Client) lets callers inject a client with a custom Transport, Timeout, or proxy. This is the composition seam for everything the SDK does not natively do (tracing, logging, mTLS).
+
"Accept interfaces, return structs" is followed correctly The SDK returns concrete *Client and concrete result types. It does not declare interfaces. Downstream consumers define their own narrow interfaces for mocking (Go proverb). This is the right default — but it could be documented in the README so consumers do not have to discover the pattern themselves.
+
Errors compose via embedding and classify via interface RateLimitError embeds APIError by value and overrides only the methods that differ. New error types can be added without touching existing ones. Behavioral classification (ErrorFamily(), IsRetryable()) lets callers handle errors by intent, not by string matching.
Medium · Composition gap

HTTP client accepted as *http.Client, not as interface

Where: options.go:58, stored on client.go:25.

WithHTTPClient(c *http.Client) requires the caller to pass a concrete *http.Client. The Go convention is to accept a narrow interface (doer interface{ Do(*http.Request) (*http.Response, error) }) so callers can substitute any type that implements Do. This is a one-line change with no behavior impact and unlocks easier mocking. The default in New() still constructs a *http.Client.

Fix Define an unexported type doer interface{ Do(*http.Request) (*http.Response, error) } in client.go, change Client.httpClient to that interface, change WithHTTPClient to accept it. *http.Client satisfies it implicitly. Backward-compatible.
Low · Power-user gap

Retry policy is configurable but not injectable

Where: client.go:69-73, options.go:49.

WithRetry(maxRetries, minDelay, maxDelay) tunes the built-in failsafe.RetryPolicy. Callers who want a fundamentally different policy (e.g., retry on 400 for idempotent operations, or use a jitter strategy not offered by the SDK) cannot inject one. Add WithRetryPolicy(failsafe.RetryPolicy[*http.Response]) for power users — defaults to nil (use the configured builder).

05Service Orientation

A common question for SDKs: should Client expose resource methods directly (client.ListProfiles()) or via a service-client sub-structure (client.Profiles().List())?

Current: flat methods on Client

client := wise.New(key)
profiles, _ := client.ListProfiles(ctx)
balances, _ := client.ListBalances(ctx, profileID)
txns, _     := client.ListTransactions(ctx, req)

Pros: shortest call sites; one type to learn; the natural shape for a library with 3–8 resources. Cons: the Client type's method set grows without bound; tab-completion gets noisier as resources accumulate.

Alternative: service-client sub-structure (AWS / Stripe pattern)

client := wise.New(key)
profiles, _ := client.Profiles().List(ctx)
balances, _ := client.Balances().List(ctx, profileID)
txns, _     := client.Transactions().List(ctx, req)

Pros: method sets are scoped per resource; the Client type stays small; easier to inject narrow service-clients into handlers (type ProfileLister interface { List(ctx) ([]ProfileResult, error) }). Cons: more types; one extra call per operation; over-engineered for 3 resources.

Recommendation Stay flat until the SDK has ~6–8 resources or until a downstream caller asks to inject a narrow service interface (the real-world trigger). At that point, the move is mechanical: extract each resource file's methods into a type ProfileService struct{ client *Client }, add a func (c *Client) Profiles() *ProfileService accessor, and keep the flat methods as thin wrappers for one release cycle to ease migration. The current architecture is ready for this move; nothing about today's design blocks it.

Service-oriented decomposition: not yet warranted

"Service-oriented" in the microservices sense does not apply to a single-process SDK. In the Go-idiomatic sense — small interfaces accepted at function boundaries, concrete types returned, narrow consumer-defined interfaces for mocking — the codebase already follows the right patterns. The one missing piece is documentation: the README should show an example of defining type ProfileLister interface { ... } on the consumer side so users do not try to mock the concrete *wise.Client.

06Roadmap

Prioritized by architectural impact. None of these are urgent; the codebase is sound today.

1

Document the consumer-side interface pattern in README

Effort: 30 min. Add a "Mocking the client" section showing how to define type ProfileLister interface { ... } at the call site. Costs nothing, prevents a class of "how do I mock wise.Client?" questions forever.

2

Document request middleware via WithHTTPClient

Effort: 30 min. Add a README section showing how to inject an http.Client with a logging/tracing Transport. This closes the "middleware gap" identified in the Scalability section without changing any code.

3

Accept a Doer interface instead of *http.Client

Effort: 1 hr. Backward-compatible. Change WithHTTPClient and Client.httpClient to accept an unexported doer interface. *http.Client satisfies it. Unlocks easier mocking for downstream users.

4

Add WithRetryPolicy for power users

Effort: 1 hr. Optional advanced knob. Defaults to nil (use the configured builder). Only add if/when requested — premature for now.

5

Move raw wire types to an internal/ subpackage (v1.0)

Effort: 2 hr. Breaking. Pair with the data-model redesign's "drop Result suffix" change. raw.Profile, raw.Balance, etc. become unexported outside the SDK. The public surface shrinks to result types only. v1.0 only.

6

Service-client sub-structure (when resource count crosses ~6–8)

Effort: 4 hr. Breaking. Convert flat methods to per-resource service structs (client.Profiles().List()). Trigger: the SDK grows past profiles/balances/transactions/recipients/quotes/transfers/webhooks, or a downstream caller asks to inject a narrow service interface. Not warranted today.

Verdict

The wise-go architecture is intentionally minimal and correctly so for its current scope (3 read-only resources, ~1.3k LOC). Coupling is tight but well-bounded; composability via functional options and injectable HTTP client is textbook; the two-layer type boundary is the single best decision in the codebase. The only structural gap — request middleware — is closable with README documentation, not code. Growth past ~6–8 resources is the trigger for service-client decomposition; everything below that trigger is over-engineering. Do not modularize prematurely.
