02Fixed on the Spot

Critical · Behavior bug · Fixed

CARD_PAYMENT with positive amount was misclassified as Refund

Where: transactions.go:classifyTransactionType.

The original code grouped CARD_PAYMENT and CARD_REFUND into a single case branch with amount-based dispatch: 

// Before — README contract violated for positive CARD_PAYMENT
case wiseDetailCardPayment, wiseDetailCardRefund:
    if amount > 0 {
        return TransactionTypeRefund
    }
    return TransactionTypeCard

The README contract is explicit: CARD_PAYMENT is always TransactionTypeCard; only CARD_REFUND is amount-dependent. The grouped implementation silently misclassified a positive-amount card payment (e.g., a reversed coffee charge) as a refund. The existing tests did not catch this because they only exercised CARD_PAYMENT with negative amounts.

Fix applied Split into two cases. CARD_PAYMENT always returns TransactionTypeCard. CARD_REFUND retains the amount-based dispatch. Added two new test cases in internal_test.go: "card payment credit still card (not refund)" and "card payment zero still card". Both would have failed against the old implementation; both pass against the fix. All 94.8% coverage preserved.
High · Consistency · Fixed

Inconsistent branded-ID formatting in ListTransactions error paths

Where: transactions.go:43-44 and transactions.go:52-56.

The two fmt.Errorf sites in ListTransactions passed req.ProfileID and req.BalanceID directly to %d, while every other call site (including the sibling mapTransaction error path at line 79-85 and all of balances.go) correctly unwraps with .Get(). The branded ID is id.ID[Brand, int64] — %d happens to print today, but the inconsistency masks any future change to the branded-ID representation.

Fix applied Both sites now read req.ProfileID.Get() / req.BalanceID.Get(), matching the rest of the codebase. No behavior change; the error messages now match their siblings.

03Open Findings (Ticketed)

These findings are documented for follow-up releases. They overlap with the data-model-review and naming-review outputs and are listed here for completeness.

High · Test gap

ListTransactionsRequest.Type filter is never tested

Where: wise_test.go (entire file).

The Type field on ListTransactionsRequest is set in the URL query string (transactions.go:32-34) but no BDD test verifies the SDK actually forwards it. A regression that dropped the filter would not be caught. Add a test in the "with a successful response" context that sets req.Type = "CARD_PAYMENT" and asserts the request URL includes type=CARD_PAYMENT.

Medium · Documentation

parseWiseDate timezone semantics are undocumented

Where: helpers.go:44-51, consumed by transactions.go:76.

Wise returns dates as "2006-01-02 15:04:05" with no timezone. time.Parse produces a UTC time.Time. Whether the original statement was UTC, the account timezone, or the currency's home timezone is never documented. A caller comparing tx.Date to a local-time value will silently off-by-one-day at boundaries. Add a doc comment to parseWiseDate and a field doc on Transaction.Date: "Returned in UTC; Wise does not transmit a timezone."

Medium · Dead value

TransactionTypeUnknown is defined but never returned

Where: types.go:209.

classifyTransactionType's default branch falls back to Credit/Debit by amount sign; it never returns TransactionTypeUnknown. The constant implies a classification path that does not exist. Either remove it (breaking change for any caller that references it) or use it as the actual fallback for unrecognized detail types so callers can detect "classification gave up." Owned by the data-model-review roadmap (Step 4).

Medium · Lying field

ListTransactionsResponse.HasMore is always false

Where: types.go:227, set at transactions.go:66.

The field promises pagination semantics that Wise does not deliver (single response). The README and AGENTS.md both document this. A caller writing for resp.HasMore { fetchMore() } will silently produce an incomplete dataset if Wise ever changes its contract. Defer removal to v1.0 (breaking change); for now, the inline comment is sufficient.

Medium · Information loss

EndOfStatementBalance is parsed but never exposed

Where: types.go:69, parsed from JSON at wise_test.go:501 but never surfaced on ListTransactionsResponse.

Wise returns a useful endOfStatementBalance in every statement response. The SDK decodes it into the raw StatementResponse struct and then throws it away. Callers who want the closing balance must make a separate ListBalances call. Consider exposing as ListTransactionsResponse.EndOfStatementBalance Money once the Money type lands (see data-model review).

Low · Style

Personal-profile name can be a single space

Where: profiles.go:33.

name := p.FirstName + " " + p.LastName returns " " when both are empty. The Wise API guarantees at least one is set for valid profiles, but the SDK does not defend against the edge case. Minor — likely never observed in practice. Worth a strings.TrimSpace if you want belt-and-braces.

Low · Type-system debt

InvestmentState, Currency, Money, DetailType (data-model review)

Where: types.go throughout.

These four type-system improvements are the core of the data-model review and are not repeated here in detail. See docs/brainstorming/2026-07-18_data-model-review.html for the full proposal and migration roadmap.

04Strengths to Preserve

+
Two-layer type system with explicit mapping boundary Raw wire types (Profile, Balance, StatementTransaction) match Wise's JSON exactly. Parsed result types (ProfileResult, BalanceResult, Transaction) expose clean Go. Mapping functions mapProfile, mapBalance, mapTransaction are the only bridge — every transformation happens in one place. This is the single best architectural decision in the codebase.
+
Phantom-branded IDs prevent cross-entity ID errors at compile time ProfileID, BalanceID, TransactionID are id.ID[Brand, T] aliases. Passing a BalanceID where a ProfileID is expected is a compile error, not a runtime bug. The .Get() unwrap is the only way to recover the primitive.
+
Behavioral error classification via go-error-family Every error implements ErrorCode(), ErrorFamily() (Rejection vs Transient), and IsRetryable() where relevant. Retry decisions are data-driven at the executor (isRetryable), not hard-coded at call sites. Adding a new error type means adding one constant and one factory case — no scattered switch statements to update.
+
Precision-safe money via int64 cents + math.Round BalanceAmount.Cents() uses int64(math.Round(v*100)). No float64 ever escapes the raw wire layer. IEEE-754 representation error is contained to the BalanceAmount boundary.
+
failsafe-go retry with backoff + selective retriability Client.executor is a failsafe.Executor[*http.Response] with max-retries, exponential backoff, and a HandleIf(isRetryable) predicate. Only 429, 5xx, and network errors are retried. Auth/not-found/client errors fail immediately. This is exactly the right retry surface for an auth-protected API.
+
Request validation before the network call ListTransactionsRequest.validate() rejects empty currency and From > To before any HTTP request is made. The error is an errorfamily.NewRejection with a typed code (wise.transactions.invalid_request) — the caller can match on family or code without parsing the message.
+
BDD tests with realistic mock API servers wise_test.go uses Ginkgo + net/http/httptest to spin up mock Wise endpoints. Each Context tests a coherent scenario (success, auth failure, rate limit, not-found, server error, cross-currency, invalid request). 94.8% coverage with zero network dependencies and a 1.42s full-suite runtime.
+
Response-body lifecycle handled correctly under failsafe-go responseCloser exists because failsafe-go's executor wraps the response — a plain defer resp.Body.Close() would not work inside the GetWithExecution callback. The //nolint:bodyclose on the request is correct: the close is deferred via the helper, not skipped. This is subtle and the codebase gets it right.
