02Advisories (Low Severity)

These did not trip any linter and have no functional impact today, but they are inconsistencies a careful reviewer would flag for cleanup. Both will be revisited in the full-code-review and data-model-review phases.

Low · Consistency

Inconsistent branded-ID formatting in error messages

transactions.go:43-44 and transactions.go:52-56

The fmt.Errorf call sites in ListTransactions pass req.ProfileID and req.BalanceID directly to the %d verb, while the sibling mapTransaction error path (transactions.go:79-85) and all of balances.go correctly unwrap with .Get(). The branded ID is id.ID[Brand, int64], so %d happens to print today, but the inconsistency is a smell and silently masks any future change to the branded-ID's underlying representation.

Fix Normalize both call sites to req.ProfileID.Get() and req.BalanceID.Get() to match the rest of the codebase.
Low · Doc drift risk

Transaction classification table vs. code path

transactions.go:148-171 vs README.md:172-183

classifyTransactionType groups CARD_PAYMENT and CARD_REFUND into a single case branch that dispatches on amount sign. The README documents CARD_PAYMENT as always mapping to TransactionTypeCard and only CARD_REFUND as amount-dependent. The grouped implementation means a positive-amount CARD_PAYMENT would currently be classified as TransactionTypeRefund, which contradicts the documented contract. The full-code-review phase will reconcile the code against the tests and README.
