02Honesty

No findings · Clean

No lying names, no hidden side effects

Authenticate(ctx) does validate auth (via ListProfiles), even though it has a network side effect. The intent in the name matches the intent of the caller. Health delegates to Authenticate and is honest about being a reachability check. GetBalance fetches one balance. ListTransactions lists transactions. No euphemisms (sanitize for delete, adjust for truncate), no misleading scope.

03Clarity & Precision

Medium · Ambiguous verb

map* mappers use the verb "map"

Where: mapProfile, mapBalance, mapTransaction, mapExchange.

"Map" in Go frequently denotes the map[K]V data structure or the higher-order slices.Map transform. The four functions here actually convert a raw wire struct to its parsed result counterpart. The intent is clear from context, but a reader's first glance could be tripped up. Stronger alternatives: toProfileResult, parseProfile, convertBalance, or profileFromAPI.

Judgment Borderline. The current names are honest and consistent with each other, and the "raw → result" intent is clear from the signature. Renaming is optional. If renamed, do all four in one pass for symmetry.
Low · Asymmetric parser names

parseWiseDate vs parseRFC3339

Where: helpers.go:44-55.

parseWiseDate is named for the vendor ("Wise"); parseRFC3339 is named for the standard ("RFC3339"). Both parse strings Wise sends. Mixing axes is a minor inconsistency. Either name both by vendor (parseWiseDate, parseWiseTimestamp) or both by standard (parseDateNoTZ, parseRFC3339).

04Consistency

High · Systemic suffix inconsistency

ProfileResult / BalanceResult vs. Transaction

Where: types.go:118, 127, 142.

The three parsed result types do not follow one rule:

  • ProfileResult — has Result suffix
  • BalanceResult — has Result suffix
  • Transaction — no suffix, collides visually with raw API types
  • TransactionExchange — sub-type, no suffix

The root cause is that the raw API also has Profile and Balance types — the Result suffix disambiguates. But Transaction happens to not collide (the raw type is StatementTransaction), so no suffix was added. The result is two rules in the same file: "result types get Result suffix" and "result types get no suffix when there's no collision." A contributor cannot predict which rule applies to the next type they add.

Fix · preferred Drop the Result suffix entirely and rename the raw wire types to live behind a clear boundary — either a raw. subpackage (raw.Profile, raw.Balance, raw.StatementTransaction) or a Wire prefix (WireProfile, WireBalance). The public result types become just Profile, Balance, Transaction — the names callers actually want to type.
Fix · minimal Rename Transaction to TransactionResult to match the other two. Cheaper, but enshrines the Result suffix as the rule and pushes the raw-types-collision problem forward rather than solving it.
Medium · Already flagged

InvestmentState constants have no named type

Where: types.go:192-195.

Every other enum (ProfileType, BalanceType, TransactionType) is a named string type with constants of that type. InvestmentStateNotInvested and InvestmentStateInvested are bare string constants — the named type InvestmentState does not exist. This is a naming inconsistency that is also a type-safety inconsistency (see the data-model review for the full fix).

Low · Pointer/value mismatch

GetBalance returns *BalanceResult but never nil

Where: balances.go:44-64.

GetBalance returns (*BalanceResult, error) and signals not-found via an errorfamily.NewRejection error, never via a nil pointer. ListBalances returns []BalanceResult (value elements). The pointer is not strictly necessary on the success path. Idiomatic Go would either return (BalanceResult, error) (value, since it is never nil) or document why the pointer is used (e.g., "future mutable methods"). This is a style nit — the current code is correct and the pointer is defensive.

05Strengths (preserve these)

+
Branded-ID naming is exemplary ProfileID, BalanceID, TransactionID with phantom *Brand types and New* constructors. The names read as the domain speaks. Compile-time entity-ID separation flows directly from the names.
+
Functional-options pattern is textbook Option type + With* functions (WithSandbox, WithBaseURL, WithTimeout, WithRetry, WithHTTPClient). Verb-first, uniform prefix, composable. This is the Go community's canonical pattern, executed without embellishment.
+
Error type names are uniform APIError, RateLimitError, AuthError, NotFoundError, ServerError — every error type ends in Error. No Exception, no Fault, no Failure. One rule, followed everywhere.
+
No Manager / Handler / Helper / Util trash cans The codebase has zero "trash-can" types that collect unrelated behavior. Every type has a single, named responsibility. This is rarer than it sounds.
+
Resource methods are verb + noun ListProfiles, ListBalances, GetBalance, ListTransactions. "List" for collections, "Get" for single. One verb vocabulary for read operations. (When write operations land, the natural verbs are Create, Update, Delete.)
+
Receiver names match type's first letter (c *Client), (e *APIError), (a BalanceAmount), (r ListTransactionsRequest), (rc *responseCloser). All receivers are short, consistent, and never this/self.
+
Internal/external boundary is clean Raw wire types are exported (because encoding/json needs them) but visually distinct from result types. Helpers are unexported. The package's wise_test.go (external) vs internal_test.go (internal) split reinforces the boundary at the file level.
